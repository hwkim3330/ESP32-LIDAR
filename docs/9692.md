# Moving to the LAN9692

Everything measured so far was done on two LAN9662s, and it ran out of ports rather than out of
ideas. Twelve ports is what the remaining questions need.

## What the extra ports buy

**Contention.** Gates are on egress, so demonstrating that shaping protects one stream from
another needs two streams arriving at one port. Two data ports can only make a chain and a chain
has one source. On twelve, the sensor and a generator sit side by side and both feed the port the
receiver hangs off — which is the port to gate.

**A second receiver.** Two boards on two ports, the same load on both, a schedule on only one.
Side by side is a more convincing demonstration than before-and-after, because nothing else can
have changed between them.

## The arrangement

```
LiDAR      --1G----> ┌──────────┐
PC (load)  --1G----> │  LAN9692 │ --100M--> ESP receiver     <- gate this egress port
ESP #2     --100M--> │          │ --100M--> ESP receiver #2  <- ungated, for comparison
                     └──────────┘
```

- **The generator is the PC.** A W5500 runs out of SPI around 10–20 Mbit/s, so filling a 100
  Mbit/s port would take five or six boards; the PC's adapter does about 95 on its own.
  `tools/load.sh` puts it on a VLAN with a chosen PCP.
- **Boards are receivers, not sources.** Only two of the bench's ESP32-S3s have a W5500 at all —
  the SuperMinis in keti-reconfig are BLE-only.
- **The 9662s are the fault injector.** A switch cannot generate traffic (neither catalog carries
  frame replication — `ieee802-dot1cb-frer` is absent; only stream *identification* is there), but
  it makes an excellent remotely-cut cable. `tools/port2-down.yaml` and `port2-up.yaml` break and
  restore a link over serial, which is what RECON's link-failure case needs.

## Order of operations

1. **Plug the switch's serial in first.** Everything below can be undone over MUP1 and almost
   nothing can be undone over Ethernet once a schedule is wrong.
2. **Ask what it is**: `s` on the board's console. The firmware carries both catalogs and picks
   its SID table from the checksum the device reports — `440057a11e66eed82bc8e838347f694c` is the
   9692. If it says it has no table for the catalog, regenerate:
   `KETI_CATALOG=<checksum> KETI_SUFFIX=9692 KETI_SHARED=no KETI_OUT=../../firmware/lidar_probe/sid_table_9692.h node tools/gen_sid_table/generate.mjs`
3. **Give the switch an address.** The 9662s use `192.168.1.10` and `.11`; keep the 9692 on
   `.10` and the firmware needs no change. First configuration is serial-only.
4. **Check the port map** with `S`. Port numbers on the 9692 are not the 9662's — keti-reconfig
   found the ESP on port 12 there. `kSwitchPort` in the firmware and the port name in every YAML
   under `tools/` have to match what `S` reports.
5. **Sensor.** It has a fixed `192.168.1.50/24` of its own now, so it needs nothing beyond a
   gigabit port. If it ever loses that, `n` on the console sets it again.
6. **Load**: `tools/load.sh <iface> 90 3` — 90 Mbit/s on PCP 3, at the receiver, on a port it will
   not mistake for sensor data.
7. **Gate**: `tools/tas-b-10ms.yaml` with the port name corrected, over serial.

## What to measure

The baseline is already established and should reproduce: **320 packets/s, 3134 µs mean, no
discards, no gaps over 6250 µs.** With the load running and no schedule, the receiver should start
losing packets or growing gaps — that is the problem TAS exists to solve, and it has to be visible
before the solution means anything. With the schedule on the load's priority, the sensor's numbers
should return to baseline while the load is shaped.

The tablet shows all of it live over BLE: packets per second, mean gap, worst gap and gaps over
threshold, alongside the point cloud.

## Traps, all of them paid for once already

- **`admin-base-time: 0` is in the past.** Restoring an all-open schedule with it is written
  successfully and then refused — `config-change-error: 1` — and the port keeps running the
  schedule you were removing. Read `current-time` from the same table and set the base a few
  seconds ahead.
- **Check `oper-gate-states`, not the write's return code.** The admin list is what was asked for;
  oper is what the port is doing. They disagree exactly when it matters.
- **`gate-enabled: false` is not a way out.** It is accepted, it clears the error, and the port
  stays shut to the class it was shutting.
- **Do not write schedules from the board.** Its CBOR is byte-identical to the CLI's — verified —
  and over Ethernet CoAP it lands with an empty operational control list, which holds one gate
  state forever. The same bytes over serial are fine. Unexplained; keep schedules on serial.
- **Never write a window that closes every class.** It closes the control path with everything
  else, and then only serial can undo it.
- **The sensor tops out at `1024x10` on the low data rate profile.** The full profile fragments
  every datagram into three and the fragment rate, not the data rate, is what drowns a W5500.
